# UniHub

A hub for learning materials: connectors bring in courses, posts and files from any portal, processors turn files into readable text, and students and AI agents read it all over REST and MCP.

It runs at [unihub.rs](https://unihub.rs): read it in the browser there, or add `https://unihub.rs/api/mcp` to an AI app as a connector, which has you sign in to the hub (MCP, below).

## Running locally

Needs Node 24+ and Docker.

```bash
cp .env.example .env   # then set BETTER_AUTH_SECRET
docker compose up -d   # postgres, redis and OpenSearch
npm install
npx prisma migrate dev
npm run start:dev
```

OpenSearch needs `vm.max_map_count` of at least 262144, which Docker Desktop has; on Linux, `sudo sysctl -w vm.max_map_count=262144`.

Search by meaning needs an embedding model: `docker compose --profile models up -d` adds a [TEI](https://github.com/huggingface/text-embeddings-inference) server with `BAAI/bge-m3` (2.3 GB, downloaded once into the `models` volume; about 2.4 GB of memory), and the `EMBEDDING_*` lines in `.env.example` point the app at it (`TEI_TAG` picks the image for your arch). The profile also starts a reranker, `bge-reranker-v2-m3` quantized to int8 (0.6 GB, put into the volume once by `reranker-init`; about 2 GB of memory), which `RERANK_URL` points at. Both models at once take about 4.5 GB, tight beside OpenSearch on a machine with 8 GB for Docker: leave `RERANK_URL` empty and start only `embedder` (`docker compose --profile models up -d embedder`). To try the wiring on a small machine, a small English embedder does: `EMBED_MODEL_ID=sentence-transformers/all-MiniLM-L6-v2`, `EMBED_REVISION=1110a243fdf4706b3f48f1d95db1a4f5529b4d41`, `EMBEDDING_MODEL=all-minilm-l6-v2-1110a243`, `EMBEDDING_DIMENSIONS=384`.

## Layout

- `src/` — the hub: its modules (`catalog`, `ingest`, `storage`, `processing`, `plugins`, `identity`, `access`, `accounts`, `web`), each used by the others only through its `contracts.ts` (a lint rule checks it)
- `web/` — the web app (Web, below), a project of its own
- `src/platform/` — what the modules run on: `database` (Prisma, `@Transactional()`), `redis`, `queues` (BullMQ), `messaging` (the outbox; `AppModule` names its transports), `role` (`APP_ROLE`, what this process runs), `errors` (one answer per kind of domain error, its reason as `code`), `validation` (a route's schemas), `search` (the OpenSearch client), `metrics` (the app's own OpenTelemetry meter, served on `METRICS_PORT`); `app.module.ts` lists the modules and wires them into the platform, `app.setup.ts` sets the app up (HTTP, MCP and gRPC) for `main.ts` and the e2e tests alike, `main.ts` starts it, or a worker with no server
- `libs/plugin-sdk` — everything a plugin may depend on, plugins never import the core directly; its `host.ts` is the hub's side (how it finds plugins), which plugins can't import
- `libs/plugins/` — the built-in plugins (`canvas`, `ocr`, `office-text`, `plain-text`), each on the sdk alone. A worker thread's file is run by node as it is in the tests, types stripped, so it and what it imports name each other's `.ts` (`rewriteRelativeImportExtensions` lets tsc take that)
- `libs/kernel` — what the hub's modules and the sdk share: values that hold the same rules everywhere (`ContentHash`, `MediaType`, `PortalId`, `PluginName`, `Instance`, `Json`) and the kinds of domain error (not found, conflict, invalid, unavailable)
- `prisma/schema/` — one schema file per module
- `npm install` generates the Prisma client and the gRPC types (`src/ingest/infrastructure/grpc/generated`, from `proto/ingest.proto`); neither is committed

A module has up to three layers, and a rule is written once, in the one that owns it:

- `domain/` — the rules. Aggregates keep their own record's invariants and record its events (catalog's `PortalFile`, `Item`); rules over several things are functions or classes of their own (`placeFile`, `PluginSet`, `Reader` with `ReadScope` and `Ban`). It also declares the ports the module needs, as abstract classes. It may import the kernel and plain libraries (zod, `node:crypto`); a lint rule keeps out other modules, application and infrastructure code, the platform, Prisma, the sdk, and all of Nest but `AggregateRoot` from `@nestjs/cqrs`
- `application/` — the use cases: load an aggregate, call it, save it in one transaction; or ask other modules over the bus and put their answers together (access's `CourseReader` only orchestrates catalog and identity). No SQL, no queues
- `infrastructure/` — what the ports are made of: Prisma repositories (a record and its events go to the outbox in the same transaction), queries that read straight into DTOs past the aggregates (`read/`), BullMQ, the file store; and the ways in (HTTP, MCP, gRPC), which only check what comes in against its schema and hand it on

## Tests

```bash
npm test               # unit specs: no database, a few seconds
docker compose up -d   # e2e specs need postgres, redis and OpenSearch
npm run test:e2e
```

- unit specs (`*.spec.ts`, next to the code) check the rules: the domain on its own, the use cases on in-memory fakes of their ports (`*.fakes.ts` beside them; `test/` has the shared ones: `FakeBus`, `InMemoryBlobs`, `sha256` of real content, plugins as discovery finds them)
- `libs/plugins/ocr`'s `tesseract.engine.spec.ts` runs the real `tesseract` with `eng`, `srp` and `srp_latn` (OCR, below): it's skipped where they aren't installed, except in CI (`CI` set), where it fails instead, so it can't be skipped unseen. On a Mac: `brew install tesseract tesseract-lang`
- e2e specs (`test/*.e2e-spec.ts`) check only what fakes can't: how records are written and read back, what the read queries find and in what order, the locks, the outbox rolling back with its transaction, BullMQ's deduplication, gRPC, each route and MCP tool once (and one bad request to each that declares a schema, since nothing else sees it is attached), the whole pipeline once (`plugins.e2e-spec.ts`), the search index's writes, the texts' and the records', and their repair (`search-index.e2e-spec.ts`), what OpenSearch answers a search, by the words and by meaning, and what of it the reranker gets (`search.e2e-spec.ts`), who finds what through the search route and tool, and their shared limit (`search-api.e2e-spec.ts`), what each user reads of a portal read with users' own accounts, by every route and by search, and a newly linked account's first run shown as it ends (`views.e2e-spec.ts`), a portal that is a site per school: rows from before given their site by a worker as it starts, one kept twice merged, and a run's and an admin's link's records of the site its settings name (`instances.e2e-spec.ts`), and of a public portal by their picks, by every route, search and MCP, with what its connector is asked for over gRPC (`picks.e2e-spec.ts`), an AI app connecting by OAuth through the API, its client's metadata document from a fake transport, and MCP with its tokens (`oauth.e2e-spec.ts`, whose app listens: the hub fetches its own keys over loopback), a file shown as a picture, by the route and the tool, on the real renderer (`file-view.e2e-spec.ts`), the app with search off (`search-off.e2e-spec.ts`), an api process adding work that only a worker does (`roles.e2e-spec.ts`), what each process serves on its metrics port (`metrics.e2e-spec.ts`), and the text index's analyzers, whose rules live in OpenSearch (`search-analysis.e2e-spec.ts`: a word in Cyrillic, in Latin and without diacritics gives the same tokens, on the OpenSearch client alone). The others boot the app as `main.ts` sets it up (`bootApp()` in `test/app.ts`, with every role unless told; `bootWorker()` for a worker) on a database, redis db, folder and search indices (`unihub-e2e-*`) of their own (`test/env.ts`), made anew for every run, with `FakeEmbedder` and `FakeReranker` (`test/fake-models.ts`) for the models, so none is downloaded (the reranker busy, so the order they check is the index's, unless a spec gives it scores), and wait for what they wait on (the outbox's events, a job's state), never for a while

## Web

`web/` is the web app: Vite, React and TypeScript, TanStack Router (file-based) and Query, Mantine, Better Auth's React client, and the API's types generated from its OpenAPI document. It's laid out by Feature-Sliced Design (`app`, `pages`, `widgets`, `features`, `entities`, `shared`), which Steiger checks; its look is `DESIGN.md`, its product `PRODUCT.md`.

The hub serves its build at `/` on the API's own origin (the `web` module, `@nestjs/serve-static`), so Better Auth's cookies need no CORS: every path but `/api`, `/.well-known` and a missing `/assets` file is the app's `index.html`, with a CSP of its own (`src/web/page-headers.ts`: scripts, styles, fonts and calls from the hub only, inline styles for Mantine, no form posts) and `Cache-Control: no-store`; the hashed assets are kept a year. `WEB_PATH` says where the build is.

```bash
cd web
npm install
npm run build          # then open the hub at http://localhost:3000
npm run dev            # or Vite on :5173, /api proxied to the hub
npm run lint && npm run steiger && npm run typecheck && npm test
```

On a file's page an image is shown as the hub's picture of it (the file itself or a member of an archive), above its text (the text read off it, if the `ocr` plugin is on, with a note that a machine read it), and a PDF's text has a Text / Page switch, kept in the address as `show=page`: Page shows the picture of the current part, paged by the same control.

Its home page is My courses: the courses the user reads, one list by name, each with the sources it comes from; a first visit with none shows the sources to link or pick from right there, as `/sources` does, unless an account the user just linked is being read for the first time (`firstSync`): then it says so in their place (the sources stay below it), and with some courses already, in a note above them, and asks for the courses and the sources again every 30 s until that read shows, as `/sources` says it beside the account. A course's page names each source it's made of and how the user reads it, searches the course, and has its files and its posts in two tabs: the files as a folder tree under the ones their portal added or changed in the last 14 days, or as one list newest first (up to 2,000; a file without a date on its portal is never new, and comes last), the one chosen in the address; a post and a file have pages of their own, where the text is read part by part (a file's part, a page or a slide, also in the address, so a search hit opens at the part it found) and an archive's members are listed, each readable. A picked course of a public portal's catalog has a "Show with" choice (Matching, below). Search (`/search`) keeps its words, course and kind (all, files or posts) in the address; with no course yet, a word that is one course's initials (ASP for "Algoritmi i strukture podataka") scopes the search to it, and removing the scope gives the word back. The account is at `/account`, and the main navigation is My courses, Search, Sources and Connect AI (where API keys are made); the user's menu holds Account, the color scheme, the language, Privacy and Sign out.

The app speaks Serbian (Latin) and English, taken from the browser and switchable from the user menu (or the header of the sign-in pages), the choice kept in the browser. Its strings are i18next namespaces in `web/src/shared/i18n/locales/<lang>/`, both languages kept in step (a test checks the keys, the plurals and that no text is empty); dates and sizes come from `Intl` through `useFormat()`.

For `npm run dev`, add `http://localhost:5173` to `TRUSTED_ORIGINS`: Better Auth refuses calls from an origin it doesn't trust. Without `SMTP_URL`, the confirmation and reset links are in the hub's log.

The API's types (`web/src/shared/api/schema.d.ts`) are generated from `web/openapi.json`, which `test/openapi.e2e-spec.ts` checks against the hub's document. After changing a route or a schema: `npm run test:e2e -- -u test/openapi.e2e-spec.ts`, then `npm run api:generate` in `web/`; CI fails until both are committed.

## Users

[Better Auth](https://better-auth.com) serves `/api/auth/*`:

- email and password, the email confirmed by a link in a mail (without `SMTP_URL` mails only go to the log)
- Google, when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set
- sign-in by QR code: a new screen asks for a code (device authorization), a phone signed in within the last day approves it. The web app's own sign-in offers it as "Sign in with your phone" (`/sign-in/phone`): its device token also sets the session cookie (client `unihub-web`; the app's `unihub-app` gets the token alone)
- session tokens as `Authorization: Bearer`, and API keys for MCP clients: only a session signed in within the last day makes one, they expire after 90 days, and a new password (a reset, a change, or one an admin sets) deletes them
- an OAuth 2.1 authorization server for MCP clients (MCP, below): its issuer is `/api/auth`, its discovery documents at `/.well-known/oauth-authorization-server/api/auth` and `/.well-known/oauth-protected-resource/api/mcp`. A user signs in on the web app's `/sign-in` and lets an app in on its `/consent`, which takes a session signed in within the last day and says how long the app stays: until a new password or 30 days unused for one that asked for `offline_access`, an hour for any other; a new password deletes the apps' refresh tokens and consents too, so each has to be let in again, and so does revoking an app's consent (`/oauth2/delete-consent`, from the web app's Connect AI page): its refresh tokens go with it, while an access token already issued lives out its hour
- users delete their own account (`/delete-user`, on the web app's Account page) with their password, or with a session signed in within the last day when they have none; their API keys, apps' tokens and consents, linked portal accounts and picks go with it

The first admin: `npm run auth:create-admin -- --email you@example.com --password '…'`. After adding a Better Auth plugin, `npm run auth:generate` updates `prisma/schema/identity.prisma`.

Every HTTP route needs a signed-in user unless it says `@AllowAnonymous()`. Admins read every course, other users the ones an admin granted them, a banned user nothing (by API key either). That's of the portals read as shared; one read with users' own accounts each user, an admin too, reads through their own account alone (Portal accounts, below), and a public one the courses they picked of its catalog (Public portals, below).

## REST API

OpenAPI at `/api/docs`. A signed-in user reads the courses they were given:

- `GET /api/courses`, then `/api/courses/{slug}/items` and `/files` (`offset`, `limit` up to 200, 50 by default; `?item=` on `/files` lists only the files attached to that post, by the id `/items` gives it). A course lists only its portal courses in the user's view, and a portal course of a portal read with users' own accounts, or one the user picked of a public portal, that no course links is a course of its own, `{portal}~{externalId}` (Portal accounts, Public portals, below), unless the user shows a pick with a course of theirs (Matching, below). Each course has `sources`, the portals it comes from, and each of its portal courses `externalId`, `url` and `via`: `account` read through the user's own account, `pick` a public portal's course they picked, `link` read through the hub's account in a course an admin made. Each file has `changedAt`, when its portal last changed it as the portal dates it (Canvas: when its content was last replaced), never when the hub read it, and null when the portal gives no date.
- `GET /api/items/{id}`: one post, as `/items` lists it (a search finds it by its id)
- `GET /api/items/{id}/text`: the post's text as the hub reads it for search: every string of what the portal sent but links and dates, HTML read as plain text, `{ text }`; 404 until the user's view opens the post, and it works with search off
- `GET /api/files/{id}`: the file and the texts made from it
- `GET /api/files/{id}/text?page=2` (`processor`): one page, slide or section of a text: the one of the processor named, else the page's longest of the texts there are
- `GET /api/files/{id}/view` (`page`, `member`): the file as a picture, for anyone who needs to see it: an image, or one page (from 1, default 1) of a PDF, as a JPEG of at most 1568 pixels a side, under the access `/content` has (a user who can't read the file gets 404, as does a page past the last). A PDF's page count is in `X-Page-Count`. PNG, JPEG, GIF (its first frame) and WebP up to 32 MiB and 64 megapixels, put on white with the EXIF turn applied, and PDFs up to 64 MiB, drawn by PDFium (WebAssembly) in a worker thread held to a 512 MB V8 heap and 30 s (PDFium's WebAssembly memory can reach 2 GiB, so at most 2 pictures are drawn at once, up to 8 more wait, and a request past that is 503 `VIEW_BUSY`); no model and no service of its own. SVG, a deck and anything else, or a file past the limit, is 422 `NOT_VIEWABLE`. 60 a minute per user, REST and `view_file` together (`X-RateLimit-*-views`); the answer is `Cache-Control: private, max-age=3600`, an error's is not cached
- `GET /api/files/{id}/content`: the file itself, as a download. `?disposition=inline` asks the browser to show it instead, and the hub agrees only for PDF, PNG, JPEG, GIF, WebP and plain text; anything else (HTML, SVG, Office files) is sent as a download whatever is asked
- `GET /api/files/{id}/members` (`offset`, `limit`): the files inside an archive the file is, in the order it lists them, each by its path (a nested archive's under its own), with the texts made from it or why it was left out (Plugins, below); `?member=lab/main.c` on `/text` and `/content` reads one of them. A member is found only inside a file the user reads, only if it was kept, and by no other way
- `POST /api/downloads` with `{ "items": [{ "file": "<id>", "member": "lab/main.c" }] }` (1 to 500 items; `member` optional): checks each item as `/content` does, keeps the request for ten minutes (in Redis) and answers 201 `{ url, name, count, size }`. One item the user may not download makes the whole request a 404, naming none; over 1 GiB in all (the bytes stored, not the size a portal reports), a 422 `DOWNLOAD_TOO_LARGE`. 10 a minute per user (`X-RateLimit-*-downloads`)
- `GET /api/downloads/{id}`: the zip, streamed, one file open at a time and stored without compression: a file under its folder, a member under its archive's name (`Labs/lab1.zip` + `src/main.c` is `Labs/lab1/src/main.c`), a name taken twice numbered (`a (2).pdf`); named for the course when all are of one, else `UniHub.zip`. Another user's, an unknown or an expired id is a 404, and each item is checked again as it is opened; one that fails partway aborts the download. 30 fetches a minute per user (`X-RateLimit-*-zips`)
- `GET /api/search?q=semafor&course=os&type=files&limit=10`: the files, archive members and posts of their courses (or of the one named; `type` `files` or `posts` for one kind alone) whose text or name matches, best first (Search, below)

Everything goes through `CourseReader` and `CourseSearch` (`src/access`), which MCP shares; 1200 calls a minute per user, searches apart, 20 a minute, and views apart, 60 a minute (`GET /api/files/{id}/view` and `view_file` together).

A user's own accounts of portals, by a token they set and never read back, are under `/api/me/portals` (Portal accounts, below); the courses they pick of a public portal's catalog under `/api/portals/{portal}/catalog` and `/api/me/picks` (Public portals, below).

Admins set the courses up (`@Roles([ADMIN_ROLE])`):

- `POST /api/courses` with `{ slug, name }`: a course
- `PUT /api/portal-courses/{portal}/{externalId}/course` with `{ course, year }`: the portal course becomes part of that course (no `year` for one that spans years); one linked elsewhere moves. Of a portal that is a site per school, it's the portal course of the site the portal's own settings read (`CANVAS_URL`, Canvas below). Linking now answers 204 whether or not the hub knows the portal course (an unknown one used to be a 404), in every portal, so it tells an admin nothing of what some user's account sees; one nothing sent yet shows once an account sends it
- `DELETE /api/portal-courses/{portal}/{externalId}/course`: unlinks it, 204 whether it was linked or known at all
- `PUT /api/users/{userId}/courses/{courseId}`: the user reads the course, named by the id `POST /api/courses` answered (users' ids from Better Auth's `GET /api/auth/admin/list-users`); `DELETE` on the same path takes it back. An id no user has is a 404, and so is granting one no course has
- `GET /api/admin/courses`: every course an admin made, by name, with its `readers` (how many users are granted it) and its `links`, each by its portal's `label`, its `mode` (`shared`, `token` or `public`), its `instance` (the school's site, null for a portal of one site), `externalId`, `year` and `name`; the name is null for a portal read with users' own accounts, since what those hold is theirs
- `GET /api/admin/courses/{courseId}/readers`: the users granted the course, by name, with `userId`, `name`, `email` and whether they are `banned` now; a course no one made is a 404
- `GET /api/admin/portal-courses?q=&offset=&limit=`: a page of the courses the shared account shows now in the shared and public portals, by name, to link (`{ total, portalCourses }`, each with its `label`, `mode` and the `course` it is linked to now, if any); `q` matches names as the public catalog does, `limit` is 1 to 200, 50 by default. Never a course of a portal read with users' own accounts

### Search

`q` is 2 to 500 characters: words, a phrase or a code identifier, in Latin or Cyrillic, with or without diacritics; `limit` is 1 to 50 results, 10 by default; `type` is `files` (files and archive members) or `posts`, both when absent. The answer:

```json
{ "results": [
  { "type": "file", "fileId": "3f0c…", "name": "l5.pdf", "path": "Predavanja", "member": null,
    "course": "os",
    "pages": [ { "page": 3, "processor": "office-text",
                 "snippet": { "text": "…", "highlights": [[12, 18]] } } ],
    "matchedName": null, "sameContentIn": ["9a1e…"] },
  { "type": "post", "itemId": "77b2…", "kind": "announcement", "title": "Kolokvijum",
    "url": "https://…", "publishedAt": "2026-10-01T09:00:00.000Z", "course": "os",
    "snippet": { "text": "Kolokvijum\n\nKolokvijum iz semafora je u petak.", "highlights": [[0, 10]] } } ] }
```

- `type` says what a result is: a `file`, a `member` (a file inside an archive the file is) or a `post`. The answer changed with posts and names: every result has a `type`, a post has none of a file's fields (no `fileId`, `pages` or `sameContentIn`), a file found by its name alone has `pages: []`, and `limit` counts posts too; a client that reads files alone skips the results of `type` `post`. A file's and a member's fields are otherwise as they were, `matchedName` added
- a file per content, the first by folder and name of those the user reads (or the one whose name matched); `sameContentIn` names the others with the same bytes
- the members of archives are looked through too, those with a text in the files the user reads: one found is its archive's file with the `member`'s path in it (`GET /api/files/{fileId}/text?member=…`, MCP: `read_file` with that `member`), after the files that hold the same bytes, and `member` is null for a file itself
- files are found by their names too, and members by their paths, by the words alone (a name isn't embedded): `matchedName` is the name (a member's path) with the words found, null when only the text matched. A file with no text (an archive, an image nothing was read off) is found by its name, with no `pages`; a file the hub has no content of isn't found
- posts (announcements, pages, assignments, a module's titles) by their text: the title, then every string the portal gave in the post's `raw` (up to 1,000,000 characters of them), but links and dates, each read as HTML as office-text reads an `.html` file (officeparser, in a worker thread of its own: no tags, scripts or styles), each text once, up to 100,000 characters. A post is a result of its own, the same text in several courses as many posts. The hub knows no portal's fields, so all of them are words, an attachment's name too. `snippet` is the best fragment of that text, a page by meaning too with an embedder; `GET /api/items/{itemId}` (MCP: `read_item`) opens the post
- `pages`: its best pages first, up to 3, each by its best fragment; `GET /api/files/{fileId}/text?page=3&processor=office-text` (MCP: `read_file` with the same `page` and `processor`) reads the whole page, as a file can have a text per processor, each paged on its own
- `snippet.text` is up to 400 characters of the page as indexed (letters composed, NFC), plain text with whatever HTML the file had: show it as text, never as HTML. `highlights` are `[start, end)` UTF-16 offsets into that text only (a page read whole may differ, when the file's letters weren't composed)
- a word is found with a typo too ("algoritmmi" finds "algoritmi"): the stems and exact forms of natural text match within an edit or two (fuzziness `AUTO:4,8`, the first letter right, so words under 4 letters stay exact; none for a query of over 16 words, which would pass OpenSearch's clause limit), an exact match ranking above a fuzzy one. Code identifiers (a word with a digit, an underscore, a capital after a lowercase letter, or a dot or slash between letters) match exactly only. A query-time rule: it needs no new index
- with an embedder (Search index, below), a file or a post is found by meaning too: a page about the same thing in other words, or in another language. Then a search answers up to `limit` results even when none has the words, the nearest by meaning, as knn always has nearest ones; `highlights` mark only the words found
- with a reranker (Search index, below), the best results (20 by default) come in the order it puts them, by how well their best snippet (a page's, else a name's or a post's) answers `q`; while it's busy with another search, or away, in the index's order
- only the files and posts the user reads right now are looked through, of a portal read with users' own accounts those whose content their own view opens, so a grant taken back, an account unlinked, or a file or a post removed, counts from the next search on. A course they don't read is a 404, as on the other routes; the search index away is a 503 (`SEARCH_UNAVAILABLE`)
- with no `OPENSEARCH_URL` there's no search: the route is a 404 and the tool isn't listed
- 20 searches a minute per user, REST and MCP counted together (`X-RateLimit-*-search`)

## MCP

`/api/mcp` serves the same reads to AI clients over streamable HTTP, as the tools `list_courses` (as `GET /api/courses`, picks shown with a course inside it; with none, a second text tells the agent why, for the user: an account of theirs just linked and still read for the first time, or no source of their own yet and the web app's `/sources` to connect one at), `list_items`, `list_files`, `list_members` (of an archive), `read_file` (page by page, of the file or of a `member`: with a `processor`, that one's text; without, every text there is of the page, each under its name, the longest first), `view_file` (as `GET /api/files/{id}/view`: an image, or a page of a PDF, as a JPEG the agent sees itself, with a line naming the file and its page; for an image, a scan, or the diagrams and formulas a page's text leaves out; counted with `GET /api/files/{id}/view` against 60 a minute), `read_item` (a post, as `GET /api/items/{id}`) and `search` (as `GET /api/search`, with the same optional `type`, its results as JSON; over its limit, a tool error). 600 calls a minute per user, however they sign in (`search` and `view_file` also count against their own limits). A request carries one JSON-RPC message as JSON: other bodies get 415, batches 400; one from a page of another site than the hub's own and `TRUSTED_ORIGINS` (its `Origin`) gets 403, and clients that send no `Origin` pass.

A client signs in one of two ways, a banned user's refused either way:

- by OAuth, as claude.ai, Claude Desktop, Claude Code and ChatGPT do: the user gives the app the URL `https://<the hub>/api/mcp`, exactly that, signs in to the hub and lets the app in. A call without a credential gets a 401 whose `WWW-Authenticate` points at the hub's discovery documents and names the scopes to ask for, `courses:read offline_access`, as `/api/mcp`'s resource metadata does (`scopes_supported`), and the app takes it from there: `offline_access` is the authorization server's, but an app that asks for what the resource names (ChatGPT) would otherwise get no refresh token and have the user sign in again every hour. The app registers by its Client ID Metadata Document (CIMD): its `client_id` is the https URL of a document it publishes, which the hub fetches. There's no dynamic client registration, so an app has to use CIMD: in Claude's custom connector dialog, choose "Use Claude's published identity" ("Register automatically" fails); in ChatGPT, CIMD (its default when the server offers it). The access token is a JWT for `/api/mcp` alone with the scope `courses:read`, for an hour; the refresh token, with `offline_access`, lasts 30 days and is replaced on every use. A token without `courses:read` gets 403 `insufficient_scope`
- by an API key (create one at `POST /api/auth/api-key/create`), sent as `X-API-Key` or `Authorization: Bearer`, for clients that don't do OAuth

## Plugins

A plugin is a Nest module that depends only on `@app/plugin-sdk` (a lint rule checks it):

- `@PollConnector({ portal, schedule })` — the hub calls `poll(ctx)` on the cron schedule for the shared account, and for each user's own account on a grid of its own (Portal accounts, below), or at once on `SyncConnectionCommand`, one run per account at a time and up to `CONNECTOR_CONCURRENCY` (4) at once per worker process; a schedule BullMQ's parser (cron-parser) refuses stops the app at start. `ctx.signal` aborts past `CONNECTOR_POLL_TIMEOUT_MINUTES` (60), when another instance has taken the run over, or at shutdown; the hub lets go of the run then, and the next one goes on from the state it saved
- `@PushConnector({ portal })` — `run(ctx)` keeps its own connection until `ctx.signal` aborts, only in a process that runs the background work (`APP_ROLE`, Running the API and the worker apart) and has `RUN_CONNECTORS=true` (the default). A run that ends or fails is started again after a second, then twice as long each time it ends soon again, up to `CONNECTOR_RESTART_MAX_SECONDS` (60); a run that stayed up longer than that starts over at a second; at shutdown all are stopped at once, each given `CONNECTOR_STOP_SECONDS` (10)
- either way, `links: ['token']` in the decorator lets users link accounts of their own on the portal by a token (Portal accounts, below); the connector then implements `identify(credential, signal)`, saying whose a credential is and when it expires, or else it doesn't compile. It rejects with `CredentialRejectedError` for a credential the portal doesn't take and `TokensNotAllowedError` for a site that takes no pasted token; anything else is the portal away, or no such portal at the address
- either way, `instances: true` says the portal is a product each school runs on a site of its own (Canvas): an account of it is linked with its site's address, which the credential carries (`credential.url`), and the hub keeps each site's records apart, stamping each record with its site (the kernel's `Instance`, an https origin) as it comes in, so a plugin neither sends nor sees it. The connector then implements `configuredInstance()`, the site its own settings read (for the shared account, and for an account linked before credentials carried their site), or else it doesn't compile; a site its settings name that isn't one stops the app at start
- every request a portal plugin makes goes through the sdk's `portalRequests` (axios options), the same whether a user or the settings gave the address: agents that check the address each connection goes to once its name is looked up, at every hop and redirect, and refuse one that isn't public (private, loopback, link-local, a cluster's), so neither a typed address, nor a redirect, nor a name that looks up elsewhere the second time (DNS rebinding) reaches the hub's own network; no proxy from the environment, which would connect in their place; up to 5 redirects, and answers of up to 64 MiB (`MAX_ANSWER_BYTES`), a file's content being the hub's to cap as it stores it; `refusedByGuard(error)` tells a refused address from the network failing, so a plugin doesn't try it again
- either way data goes in only through `ctx.ingest`, bound to `ctx.connection` (the portal and account). `ctx.account` says whose the run is: `shared` (the plugin's own settings), or a `user`'s own account, whose `credential()` the run reveals only to ask the portal; a run that rejects with `CredentialRejectedError` marks the account `revoked`. An account sends what it sees as a whole: `courses(records)` after a listing that went through (a record refused is left out and named, its pass to skip, and what the account saw of that course stays), then a `pass(course)` each, its `item()`s and `file()`s, `end(gone?)` naming what a listing that went through no longer has (a listing that failed takes nothing away), and, once every pass of the run has ended, the `content()` of the files `file()` answered `fetch: true` for (so when a pass ends says nothing of what the hub had of another course's files). Only the shared account may also send record by record and remove (`course`, `item`, `file`, `content`, `removeItem`, `removeFile`), as gRPC connectors do. A record it refuses rejects with `InvalidRecordError` (fix it or skip it) or `UnknownReferenceError` (send what it refers to first), and their `reason` says which rule it broke, the same reasons gRPC connectors get
- `@ContentProcessor({ name, version, accepts, heavy? })` turns file content into text for models, once per content and version whichever files hold it; it gets only files it accepts, and `input.matched` says which `accepts` entry the file matched (its extension first, then its media type). The sdk's `readUpTo` reads content up to a limit and `firstMessage` waits for a worker thread that parses it, as the built-in processors do. `heavy: { timeoutMinutes }` marks one backed by a model that runs only while there's work for it: its jobs wait in the `models` queue for a batch run (Heavy processors, below), and `input.signal` aborts past `timeoutMinutes` (a whole number, at least 1) and at shutdown. Without it the processor runs in the `plugins` queue with the rest
- `@ContentUnpacker({ name, version, accepts })` lists the members of a container (an archive): `unpack(input)` yields each one's `path` as the container names it, its `content` as a stream, and its `size` and `mime` when the container says; `input.signal` aborts past the hub's time. One unpacker takes a format: two that accept the same extension or media type stop the app at start, and a file one takes by its extension and another by its media type goes by its extension. An extension is a file's last (`.gz` of `labs.tar.gz`): an `accepts` entry of two (`.tar.gz`) stops the app at start
- `@Aggregator({ name, topics })` reacts to messages (`item.ingested`, `item.removed`, `file.content-stored`, `file.removed`) and reads the rest through `HubReader`; `handle()` is typed by the topics, so one that doesn't handle them all doesn't compile

Built-in processors, each parsing in a worker thread of its own with 512 MB of heap:

- `office-text` (`libs/plugins/office-text`) turns pdf, pptx, docx, odt, odp, html, rtf and epub into text: part n of a pdf or a deck is page or slide n (empty where it has no text), a document or a page has a part per section (a long one goes on in the next part past 10,000 characters, a page's scripts and styles are left out). It's given up to 100 MiB of content and 3 minutes
- `plain-text` (`libs/plugins/plain-text`) turns source code, plain text, markdown, Jupyter notebooks and data files (csv, json, yaml, xml…) into text, taken by extension or media type (listed in its `formats.ts`). It finds the encoding (UTF-8, UTF-16 with or without a BOM, windows-1250 and 1251, ISO-8859-2 and 5, DOS's cp852 and cp855), line by line in a file that is UTF-8 in places and a code page in others; lines end in LF and letters are composed (NFC). Markdown up to 1 MiB and notebooks (markdown and code cells, with their text outputs but no pictures) have a part per section, from one heading to the next (a `#` in a code block is none); the rest comes in whole lines, up to 10,000 characters a part, a longer line cut at a space or else at 10,000. A text file's parts joined give it back. Binary content, minified code (`*.min.js`, `*.min.css`) and files past 16 MiB (64 MiB for a notebook) get no parts; it's given a minute

The two take different formats. A file they both match, an `.html` a portal calls `text/plain`, has a text of each, and a page asked for without a processor is the longest of their texts (`read_file` gives both). Results are stored per content hash and processor version, and a reconcile at startup and every day queues whatever is missing.

A container a file holds (an archive) goes to the unpacker that takes it, once per content, unpacker version and the hub's limits (`LIMITS` in processing's `tree-budget.ts`), in one walk that opens the containers in it too, each by the unpacker that takes it, up to 3 deep and each content once. Each member is stored as a content of its own and processed as a file of its name; the tree of their paths is kept per container content, a nested container's members under its path (`team1/lab.tar.gz/src/main.c`). A walk stores up to 256 MiB in all and 100 MiB of a member (less with a lower `STORAGE_MAX_FILE_MB`), counting the bytes written rather than the sizes the container declares (those of a member left out once it's past them too), and lists up to 10,000 members; one past those is listed with why it's left out (`TOO_LARGE`, `OVER_BUDGET`), as is a path listed twice (`DUPLICATE_PATH`) and a container too deep to open (`TOO_DEEP`). A path gets `/` between folders and composed letters, or is left out unlisted: absolute, on a drive, with a `..`, a control character or one that turns text around. So is noise: anything under or named with a dot (`.git`, `.DS_Store`), and `node_modules`, `__MACOSX`, `bin` and `obj`. A container that breaks partway keeps what was listed, its tree cut short with the reason, and is walked again only for another unpacker version or other limits; a walk past 10 minutes fails as a processor's job does, and one stopped at shutdown goes back to wait. The store failing (its file system's errors) fails the job too, which retries. The reconcile queues the trees missing or made under other limits, and the processing their members lack.

The built-in unpacker, `archives` (`libs/plugins/archives`), takes zip, tar, tgz and gz files by extension only (a portal calls a docx or an epub `application/zip` too), with yauzl, tar-stream and zlib. It lists their regular files, not folders or links: a zip's by the names it encodes (UTF-8, whether it says so or not, as a Mac's don't, else CP437), leaving out entries it encrypts or packs other than stored or deflated; one of strong encryption, which yauzl can't list, cuts the zip short there. A bomb is the hub's to stop, by the bytes a walk writes. A zip is read whole up to 100 MiB, a tar unpacks up to 1 GiB, and a `.gz` holds a tar when its name less the `.gz` ends in `.tar`, one file of that name otherwise.

Each aggregator gets a queue job of its own per message, each processor one per content it takes and each unpacker one per container, so one failing plugin only retries itself; a job that gives up for good is logged. Built-in plugins are listed in `src/plugins/enabled.ts` and turned on by name in `PLUGINS`; `test/fake-plugins.ts` shows one of each. A processor taken out of `PLUGINS` keeps what it made, in postgres and in the search index, but its texts are neither read (a file's texts, its pages, with the processor named or not) nor found until it's back on; then they are again, none made anew.

### OCR

`ocr` (`libs/plugins/ocr`, on in `PLUGINS`) reads text off pictures with Tesseract, run as a child process in the worker (no network, no service, nothing written to disk), and gives it as another text of the file, a page asked for without a processor being the longest of the texts. It reads:

- an image (png, jpeg, gif, webp, tiff): one part
- a PDF's pages whose text layer has under 30 characters (not counting white space), drawn by PDFium at 200 DPI: part n is page n, empty for a page not read
- a pptx's slides with under 30 characters of text, their pictures (up to 6 a slide, none under 48 pixels a side): part n is slide n, in the order the deck lists them

Nothing read is no parts, stored like any result, so it isn't queued again; so is a file that can't be read (too large, corrupt, protected, a page that fails or runs out of time), with a warning in the log naming it. Only the `tesseract` binary missing fails the job: **an image built without Tesseract fails these jobs**, and the image has it with English and Serbian (Cyrillic and Latin).

`OCR_LANGUAGES` (default `eng`) is a comma-separated list of candidates, each `detect` or `detect=read`, a Tesseract `-l` value (`srp_latn+eng`). A picture is first run through every candidate's `detect`, and the one with the highest mean confidence wins; if it has a `read` that differs, the picture is read again with that. That is how the script is told: one pass with `srp+srp_latn+eng` turns Latin lookalikes into Cyrillic (ENIAC becomes ЕМАС), while separate passes compared by confidence told it right on all 37 samples, where Tesseract's own detection got three wrong; and `srp=srp+eng` as the final read keeps Latin terms on Cyrillic pages. Production sets `srp_latn+eng,srp=srp+eng`. A language is one more `tesseract-ocr-*` package in the image (`tesseract-ocr-deu`, …), and its name in the list.

Limits: a PDF or deck up to 100 MiB, an image or a deck's picture up to 30 MiB and 100 megapixels, at most 500 pages or slides and 30 minutes a file (the rest stay empty, with a warning), 60 seconds a Tesseract run, and two files at a time, one thread each: two cores at most.

`reader` and `vision` (`PLUGINS`, each on its own) read the same files the same way, but with a model: `reader` reads a page off it, `vision` says in two sentences what a picture shows (formulas as LaTeX). Each takes the address of an OpenAI-compatible server that takes images (llama.cpp's, with its model), `READER_URL` and `VISION_URL`, an http or https URL that is required once the plugin is on. They are heavy processors: their jobs wait in the `models` queue and run only in a `models` batch with the model server beside it (Heavy processors, below), one picture at a time, each fitted inside 1600 pixels and sent as a JPEG. A server that can't be reached or is still loading (5xx) pauses the queue with no attempt spent; a picture the server refuses (4xx) or takes over 10 minutes over is left empty, with a warning. At most 200 pages or slides and 170 minutes a file, 180 minutes a job. Their texts are another text of the file, each under its own name, and the reader shows them as made by a machine.

### Search index

With `OPENSEARCH_URL` set, the texts also go into an OpenSearch index, its analyzers taking a word in Cyrillic, in Latin and without diacritics alike. With an embedder (`EMBEDDING_URL`, a TEI server), each chunk goes in with its vector too, in `<OPENSEARCH_INDEX_PREFIX>-texts-g1-<EMBEDDING_MODEL>-<EMBEDDING_DIMENSIONS>`; without one, by the words alone, in `<OPENSEARCH_INDEX_PREFIX>-texts-g1-bm25`:

- each page is cut into chunks of up to 1200 characters, at a paragraph, line or word break, its letters composed (NFC), and embedded 8 at a time
- a `search-index` queue, one job at a time, writes the newest version of each text the processors store: its chunks, then a manifest that says the text is in whole, then it drops its other versions, a newer one postgres lost too. While OpenSearch, the embedder or the database is away (an embedder refusing connections, hanging up or not found, or answering 429, 502, 503 or 504), or OpenSearch's disk is past its flood stage, the queue waits 30 s at a time without spending attempts, and logs it as an error every 10 minutes it goes on. On shutdown the text being embedded is let go of at once and goes back to wait, also without spending an attempt, so a restart doesn't wait out a long one
- the embedder is asked its model (`/info`) before its first embed: `EMBEDDING_MODEL` names the model and its revision as it serves them (`bge-m3-5617a9f6` for `BAAI/bge-m3` at `5617a9f6…`), and a server of another one fails every embed, saying which, so vectors of two models never mix in one index. Another model is another `EMBEDDING_MODEL`, so another index, filled from postgres next to the old one; a vector of other than `EMBEDDING_DIMENSIONS` fails too
- besides the texts, it holds records: each post's text (made from its title and `raw`, Search above), cut and embedded as a page is; each name of a file with content; and the paths of the members a tree kept, a document each. A record is kept under what it's of (`kind`, `record`: the post's or the file's id, the archive's content hash), with a manifest once it's in whole that says what it was made from (`fingerprint`: a post's when catalog last changed it and the version of the text's rule, `POST_TEXT_VERSION`, a file's name and content, a tree's unpacker, version and limits) and a `digest` of its chunks. Its chunks carry a hash: a name's or a path's that of the content it names, so a search answers them with that content and a file found by its text and by its name is one result; a post's one of its own (`post:<id>`), each post a hit apart. Names aren't embedded, so they're found by their words alone
- a post's job is queued with each `item.ingested` and `item.removed` the outbox publishes (under the message's id, so a change while one runs is another), a file's with each `file.content-stored` and `file.removed`, a tree's once it's unpacked, on the same `search-index` queue. Each indexes the record as it is when it runs, or takes it out: a post removed, a file removed or without content. One whose chunks come out as the index has them (its `digest`), a post edited past its text, gets its fingerprint alone written, nothing embedded. Otherwise its chunks go in, then the manifest; one that replaces a record (its manifest there, or its first chunk, a write that failed partway) waits for the index's refresh, as a text's does, and then its chunks of another digest go. One written the first time, as a backfill writes them all, replaces nothing (a get sees a document at once, a search only after a refresh), so it waits for none and is found within the second. A rename has no event: the hourly reconcile finds it
- a reconcile at startup (tried again every 30 s while OpenSearch is still starting, for 10 minutes) and every hour queues what the index lacks of the texts of the processors that are on, and what it still holds of other versions or removed texts; and every post, file with content and tree it lacks or holds made from something else (a post by when catalog last changed it, so no post's `raw` is read), and the records it holds of none
- `SearchTextsQuery(text, among, limit)` (processing's contracts) looks through what it's given, and nothing else: the texts of the `contents`, by the processors on (`PluginCatalog`), as the reads do, and the records of the `posts`, the `files` and the `archives` (each kind by its ids, a filter of its own). What a processor turned off has in the index stays there, filtered out in the query, so turning it back on finds it again at once, nothing embedded anew; posts and names are no processor's. The index knows nothing of who reads what: access's `CourseSearch` gives it the contents of the files the user reads and of their archives' members with a text, the files themselves, their contents as the archives, and the posts of the courses the user reads, so one account's view could later be given the same way, as its own ids. It answers those whose texts have the words in any analysis (exact forms, Serbian and English stems, code identifiers) and, with an embedder, those whose chunks are nearest the query's meaning: a hybrid query of the two, the contents' filter on both, each part's scores made 0 to 1 and then averaged, a half each (the `<OPENSEARCH_INDEX_PREFIX>-hybrid` search pipeline, put whenever the index is made sure of). The query's vector comes from `EMBEDDING_QUERY_URL`, a server of its own with the same model so a search never waits behind indexing (`EMBEDDING_URL` unless it's set), within 3 s; past that, while it's away or when it serves another model, the search goes by the words alone and the log says why. Best first, at most `limit` contents (a post's text one), each with its best pages (up to 3, each once, by the best of its chunks there) and its records found (up to 3, each once by its best chunk, a tree's members apart), each with a snippet of up to 400 characters. `highlights` are UTF-16 offsets into the snippet's own text, which comes from the page as indexed (NFC), plain text with whatever HTML the source had, to be shown as text. OpenSearch away, or a search past 5 s, is `SEARCH_UNAVAILABLE` (503); one that finds the index or the pipeline gone makes them again, and finds nothing until the reconcile fills the index
- with a reranker (`RERANK_URL`, a TEI server of a model that reads the query and a text together, as `bge-reranker-v2-m3`), the index is asked for at least `RERANK_CANDIDATES` contents (20 by default, up to 50), and those come in the order it scores them, each by its best snippet, ties as the index had them and the rest after. On a CPU it's slow, the more so the more snippets (20 take about 1.3 s on 6 arm cores, 3 to 4 s on 8 to 4 amd64 ones: Deploying search, below), so it takes one search at a time: another meanwhile keeps the index's order at once, and so does one past 5 s or while it's away, with a warning in the log, or one it fails otherwise (another kind of model at `RERANK_URL`, an answer that can't be read), with an error
- the index is made of postgres alone and needs no backup: one lost or deleted is made again (with the pipeline) by the next write and filled by the next reconcile. The `g1` in its name is its generation, raised when its analysis, a field it has or the chunks change; a field added is put into the index there instead (`PUT _mapping`, whenever the index is made sure of), its documents kept as they were, as the records' fields were. The new one, or one of another model (`EMBEDDING_URL` set for the first time too), fills next to the old, which is then deleted by hand (`curl -X DELETE localhost:9200/unihub-texts-g1-bm25`; on a server, Deploying search). Searches go to the new one at once, so until the reconcile has filled it (one text at a time, each embedded 8 chunks at a time: hours for a large corpus) they answer only what it holds so far

Without `OPENSEARCH_URL` none of this is loaded, and processing runs as it did; `SearchTextsQuery` answers `SEARCH_OFF` (503).

### Canvas

The `canvas` connector (`libs/plugins/canvas`) polls a school's [Canvas LMS](https://canvas.instructure.com/doc/api/). Read as `shared`, it polls every hour on the hub owner's own personal access token, one account: whoever the hub lets read a course reads it as the owner sees it. Read with users' own tokens (`canvas=token`, Portal accounts, below), each user links their own school's Canvas, by its address and a token of their own, one Canvas per user; it polls each user's account on its grid, as that user sees their courses, and needs no `CANVAS_TOKEN`. Each Canvas's records are kept apart, as that site's (`instances`, Plugins above). It isn't in `PLUGINS` by default, and turning it on is the owner's call: the school's Canvas policies come first. Instructure's API policy has the school told when an app hands Canvas content to generative AI (the hub's MCP does) and doesn't let one user's access serve others, so tell the school (its Canvas admins or IT) what the hub reads and who reads it, and until the school or the teachers say otherwise, grant its courses to no one but yourself.

To turn it on:

- in Canvas, Account → Settings → Approved Integrations → New Access Token, with a purpose and an expiry date. Some schools don't let students make tokens or cap how long one lasts, and Canvas has revoked tokens in bulk before: the connector warns in the log 14 days before the token expires, and a run fails with "canvas token expired or was revoked" once Canvas no longer takes it
- set `CANVAS_URL` (the school's Canvas, `https://canvas.example.edu`, https only as the token goes with every request, port 443: in `.env` or `deploy/.env`, never in the repo) and `CANVAS_TOKEN` for a Canvas read as shared; with users' own tokens neither is needed, but `CANVAS_URL` is the Canvas of accounts linked before each kept its own address. If you like, `CANVAS_USER_AGENT` (Canvas refuses requests without one; `course-sync` by default, which names neither the hub nor you). Then add `canvas` to `PLUGINS`

What it reads, of the courses you're active in:

- the course, by its own name rather than your nickname for it, with its code, term and dates in `meta` (to pick the year by when linking it)
- modules with their items, announcements, pages and assignments (read as shared with the dates for everyone, not your own; with a user's own token, theirs), as items `module:`, `topic:`, `page:` and `assignment:` with the portal's id; a user's own account's modules leave out which items they list, which differs from one account to the next
- files with their folders' paths, linked to their page in the course and dated by Canvas's `modified_at` (`updated_at` where it gives none); the course card's picture (Canvas's top-level `course_image` folder) is left out, and files in its top-level `unfiled` folder, where it puts files uploaded without one, sit at the course's root; an announcement's attachments name it. Content is downloaded once every course's pass has ended, only when the hub asks for it (a new file, or a new size or date; with users' own tokens, by one account's run, Portal accounts), and a file locked for the token's user is sent locked and waits for a later run
- a hidden Pages or Files tab keeps those lists out, but the pages and files the modules link to are read one by one
- read as shared, only what the whole course sees: no announcements for some sections, no assignments for only some students; with a user's own token, what that user sees of them. Either way no group discussions, and no field that says how the user stands (read, done, locked, their submission)
- not discussion replies, quizzes, grades, submissions, the calendar, groups, finished courses, or files linked only from inside a page's text

A record gone from a listing that went through to the end is gone from the account's view (removed, read as shared). Nothing is for a listing that failed, was cut short or refused, or a tab hidden since, nor for a course Canvas fails on or whose record the hub refuses; a course no longer listed is gone from a user's account's view with all it had, and keeps its records read as shared. A course Canvas fails on (a listing still failing after the retries, a bad request) is skipped for that run and logged, the others go on, and the run is marked failed once they're through; a request that gets no answer after the retries (the network, a page that isn't JSON) fails the run there. A download Canvas refuses or fails, one that gets no answer after the retries, and one cut off partway are logged and tried again the next run. It sends one request at a time, 100 records a page; a throttled or failing request, or one the network failed, is tried again after about 1, 2, 4, 8 and 16 seconds; a request has a minute for its answer, redirects included, and then fails once a minute goes by without a byte read (for a download, also when the hub's storage takes none for that long); and each request waits 2 seconds while the token's quota is low. The token goes to the Canvas it's of only (`CANVAS_URL` for the owner's, the one its user linked it with for theirs): a link Canvas gives to another address is refused and fails the run, and a redirect to one leaves the token out. Every request goes through the sdk's guard on what a portal plugin's requests reach (Plugins, above); an address it refuses fails at once, not tried again. That's about ten requests per course an hour, and the files that changed.

Canvas's rows from before accounts kept their Canvas, its records and users' accounts with no site, are `CANVAS_URL`'s: a worker gives them its origin as it starts, before any Canvas run, and an admin's link to a Canvas course waits for it too; all in one transaction, and with none left it changes nothing (`npm run instances:adopt` does the same alone, after `npm run build`). A record kept both ways (an app from before still running, an admin's link before the worker came) is one: the one runs sent stays, and what named the other names it; one runs sent both ways is left and logged. An account from before reads the Canvas it was given then, whatever `CANVAS_URL` says since.

### Portal accounts

How a portal's accounts are linked is set per portal in `PORTAL_LINKS` (`canvas=token/admins, moodle=token, catalog=public`), and the name each is shown by in `PORTAL_LABELS` (`canvas=Canvas, catalog=Course catalog`; its id when not named):

- `shared`, every portal's unless it says otherwise, as before: the one account the plugin's settings give (`CANVAS_TOKEN`), read by whoever an admin lets read a course
- `token`: each user links an account of their own by pasting a token the portal gave them; `/admins` lets only admins link one
- `public`: a site anyone may read, with no login, whose connector sends its whole directory of courses as its one account (shared); each user picks the courses they read of it (Public portals, below). Only a connector over gRPC takes it, as it's asked which courses are wanted (`Wanted`, External connectors), and none needs naming it
- only `shared`, `token` and `public` exist for now: `PORTAL_LINKS` refuses any other mode (a portal's consent page, a user's own connector). The app doesn't start with a mode the portal's connector doesn't name (`links`, Plugins above), nor with `public` for a portal no gRPC token is for

The token is a setting that's written, never read:

- `PUT /api/me/portals/{portal}/token` with `{ "token": "…" }`, and on a portal that is a site per school (Canvas) `"url"`, the school's address (any page of it, its scheme left out too, made its origin; https, port 443, a DNS name): 204 once the portal's connector says whose it is (`identify`) and when it expires. Of the portal's user only their id on the portal is kept, never a name or an email. It needs a session signed in within the last day, as making an API key does (403 `SESSION_NOT_FRESH`), and takes 10 a minute per user (`X-RateLimit-*-link`), as each one asks the portal. A portal not linked by token, or one for admins to anyone else, is a 404; a `url` missing on a portal of sites (`URL_NEEDED`), given on another (`URL_NOT_TAKEN`), or no https site, a 400; a token the portal doesn't take a 422 with `code` `TOKEN_REFUSED`, and one a site takes none of (a Canvas Instructure hosts) a 422 `TOKENS_NOT_ALLOWED`; the portal away, no such portal at the address, or no answer within 30 s, one 503 (`PORTAL_UNREACHABLE`). A token of the same portal user of the same site keeps the account; another's, or one of another site, makes a new one in its place: one account per portal per user
- `DELETE` on the same path unlinks: the account and its token go together, and so do what its runs saved and what it saw, as for one replaced by another portal user's; what no other account sees is removed with it, out of the search index at once
- `GET /api/me/portals`: `[{ portal, label, mode, linked, instance, status, expiresAt, picked, firstSync }]`, for each portal you may link an account of or pick courses of, and each you have an account of; `instance` is the site your account was linked with (null when not linked, or for a portal of one site), `status` is `linked`, `expired` (past `expiresAt`) or `revoked`, null when not linked. Of a public portal, `linked` is false and `picked` the number of its catalog's courses you picked; `picked` is null for any other. `firstSync` is true while your account of it reads and has had no pass shown since it was linked (its first run is at it; a pass is a course listing, so a course's posts and files may follow after it ends), with no counts or times, which could tell how long a pass took. Never the token or any hint of it, and nothing of anyone else: each user's account is their own, so the same portal user linked by two people is no conflict
- no MCP tool sets or shows any of it, and the token goes in no log, error, job, Redis, the outbox or sync state. A deleted user's accounts go with them

Tokens are sealed with AES-256-GCM (`node:crypto`), each for its own account and with the site it's of, so the address a token goes to can't be changed without the keys either, under `PORTAL_CREDENTIALS_SECRETS="2:…,1:…"`: keys of their own (`openssl rand -base64 32` each), never `BETTER_AUTH_SECRET`, needed once a portal links by token. The highest version seals, any listed opens: to rotate, add a higher version and keep the older ones while tokens sealed under them remain (a token set again is sealed under the new one). A version taken off leaves what it sealed unreadable, the copies in old backups too. Whoever holds both the database and the keys can open them; the hub has to, to use them.

What portals send is kept as versions: each course, post and file as the accounts that see it saw it, and a sight per account and version, since when its view shows it, whether it may be opened (not locked for it) and since when, and since when it's gone from it. Catalog knows accounts by ids alone, never users. A portal that's `shared` is read as it always was, with no delay or hold before anything shows, admins reading every course and the others the courses granted them: its records' one version is the shared account's, under the record's own id and changed in place, as records were before. Versions no account sees any longer are kept.

A portal linked in another mode is read with its users' own accounts, every read and search cut to what the user's own account sees (access's viewers: their accounts of those portals that are linked and not expired, none for a banned user):

- grants give nothing of it, and admins read it only through accounts of their own; the shared account's view of it, from before it was linked so, is read by no one
- a course a user reads holds the portal courses their account sees, and those parts alone; a portal course no course links is a course of its own, by the slug `{portal}~{externalId}` (`canvas~101`), or for an id of other than URL-safe characters `{portal}~~` and 22 characters of a hash of it: stable, and never an admin's slug or another's
- a post or a file is the version the user's account sees, under that version's id: two accounts that see one differently read two ids, and a post shown, or a file's post, is always the user's own version
- a file's content (`hasContent`, the bytes, its texts and members) and what search finds of files and posts open only once the user's view opens them (`openFrom`); a file locked for their account stays listed, and closed
- another account's post, file or course answers as one that isn't there, the same 404

Each linked account is polled as soon as it's linked, then every `VIEW_MINUTES` (60) at an offset its id gives: a grid of its own, so when one passes tells nothing of another, and the run asks the portal as that user alone, never anything outside their own view. A run reads the account's courses, then each course's listings, its records sent as one pass: the account's view of the course is then what it sent, and what it saw before but what a listing that went through no longer has. A pass names what's gone (`end(gone)`) rather than standing for the whole view: what a listing that failed, was cut short or was never saved had stays, for a user's account as for the shared one, so a portal that's away for a moment takes nothing out of anyone's view, and a connector that can't tell gone from not listed this time takes nothing away. What a pass finds shows at the run's slot plus `PUBLISH_DELAY_MINUTES` (10, under `VIEW_MINUTES`), whatever the pass did, so how long it took and whether the hub had it already tell no one anything; a pass that ends past that shows at the next slot. An account's first run, one that starts with no pass of it shown since it was linked (a token of another portal user's makes a new account, so it has a first run too), shows each pass when it ends instead: the user knows when they linked, and that first view comes from their own account, so its time tells no one anything, while every later run keeps the slot, so when a new post shows says nothing of when someone else's account brought it. Content opens `HOLD_MINUTES` (15) after a pass shows, a first run's too, the same for content new to the hub and content it had: the hold is what hides whether the hub had the bytes already. Each is a whole number of minutes, `VIEW_MINUTES` from 5 to a day. An account that's expired or revoked isn't polled, nor read; a run the portal refuses the token of marks it revoked, until it's linked again (the token that run had: one linked meanwhile stays linked).

Records seen alike by several accounts are one version (by a hash of the record), so a section's post is in the views of the accounts that list it and in no other, and one that two accounts see differently is two. A file's bytes are fetched once per version of them (its size and date on the portal): by the first run that sees it open and takes a lease on it (in Redis, for as long as a run may take, `CONNECTOR_POLL_TIMEOUT_MINUTES`), once every pass of the run has ended, while the others go on without; one whose bytes the hub has already, from another account or another version, gets them at once. They're stored and processed once per content, as every file is.

What sharing the work still tells, by its timing and load, never who or what:

- timing past the hold: content opens at the hold whether the hub had it or fetched it for this account, unless fetching, processing and indexing it take longer than `HOLD_MINUTES` (a first link of a large course nobody had, an embedding backfill); then its texts and search hits come later, which says it was new to the hub
- aggregate load: answers are slower while others' runs and searches load the server, which one server can't hide; the search index's word statistics are the whole index's
- the reranker's busy fallback: a search while another is reranked keeps the index's order (Search index, above), which says someone else is searching

The Canvas connector takes `token`; what that means on a hosted or a self-hosted Canvas is in Canvas tokens, below.

### Public portals

A portal set to `public` is a site anyone can read, its connector outside the hub (External connectors, below): it sends every course of the site's directory, as its one account, and those are the portal's catalog. Each user picks from it the courses they follow, and reads those, with no grant:

- `GET /api/portals/{portal}/catalog?q=&offset=&limit=`: `{ total, courses: [{ externalId, name, url, picked, isNew, into, suggestedInto }] }`, the catalog's courses by name (numbers by value), those whose name has `q` (up to 200 characters, matched in any case, with or without diacritics: `racunar` finds `Računarske mreže`, `dacki` finds `Đački`), `limit` up to 200 and 50 by default. `picked` says you picked it, `isNew` that the hub first saw it within 14 days, and of a course you picked `into` and `suggestedInto` which of your courses it's shown with and which it may be (Matching, below), null for the others and for one an admin linked to a course, which stays in it. A portal that isn't public is a 404
- `PUT /api/me/picks/{portal}/{externalId}`, with no body or `{}`: 204, picked, and picked again it's no new pick. `{ "into": "canvas~297" }` shows it with that course of yours, `{ "into": null }` on its own again, and left out it stays as it was (Matching, below). A course the catalog doesn't have, or a portal that isn't public, is a 404; past 100 picks a 422 with `code: TOO_MANY_PICKS`, and an `into` that's no course you read through your own account a 422 with `code: NOT_YOUR_COURSE`. The 100 are the picks `GET /api/me/portals` counts: those in a public portal's catalog now
- `DELETE` on the same path: 204, whether you had picked it or not, whatever the portal's mode is now
- both take 30 a minute per user (`X-RateLimit-*-picks`), as each may have the connector sync another course
- a course picked is read by the picker by every route, search and MCP, as a course of its own (`catalog~101`), or inside the course an admin linked it to: its posts, files and texts, through the portal's one account. A grant gives none of it, an admin reads only what they picked too, and a banned user nothing. A pick of a portal no longer public reads nothing
- a deleted user's picks go with them (identity's event), and each course they leave with no pick starts its grace (below)
- no MCP tool picks or lists the catalog

A course picked is wanted: its connector learns it by `Wanted` (External connectors, below), and sends its posts and files from then on. Once no one picks it, it stays wanted 14 days more, so a pick meanwhile finds its sync where it left off; the hourly reconcile then drops it, and starts the grace of a course no pick keeps whose grace didn't start (two last picks gone at once). A course no longer wanted isn't removed: the connector keeps it as it was, its state too. Nothing of who picks what, or how many, leaves the hub, and the timing does tell one thing: a course someone else picked shows its posts at once.

### Matching

The same subject is often a course on two portals: the one a user reads through their own account, and the one they picked of a public site. Nothing on either says they're the same, so the hub doesn't guess by name: people decide, and the hub only moves cards. Where a course shows never changes what the user reads, only in which course they find it, the same by every route, search and MCP (`regroup`, `src/access`):

1. an admin's link comes first: a picked course an admin linked to a course is in that course, for everyone who picked it
2. then the user's own choice: a pick they show with a course of theirs (`into`) is inside that course, after its own portal courses, its slug no longer a course's. The choice is kept by the portal course of their own account it goes with, so it follows that one into a course an admin links it to, and while the user doesn't read it through their account (unlinked, expired) the pick is a course of its own again
3. else the pick is a course of its own, as before

A course to show a pick with is one the user reads through their own account; admins can't see what users' accounts hold, so there's no admin queue of users' pairs. The catalog suggests one for each course picked (`suggestedInto`): the course of the user's own that shares the most files with it by content, at least 2, counting only the files the user's own view opens of both, so it says nothing of what anyone else reads. The suggestion is the user's to take: nothing is moved until they choose.

### Running a hub with users' own accounts

The reference above says what the code does; this is what an operator decides. Everything here is off until a portal is set to `token`.

#### Link modes

| `PORTAL_LINKS` | Who gets in | Credential |
|---|---|---|
| a portal not named, or `canvas=shared` | the one account the operator configures (`CANVAS_TOKEN`); grants decide who reads | the plugin's settings |
| `canvas=token` | every user may link an account of their own | a token each user pastes on the web app's Sources page, with their school's Canvas address |
| `canvas=token/admins` | only admins may link; everyone else gets a 404 | the same |
| `catalog=public` | every user picks courses of the site's catalog; no grant | none: the connector reads a site anyone may read |

- A token is write-only: `PUT` replaces it, `DELETE` unlinks, nothing reads it back (no API answer, log, error, job or MCP tool shows it or a hint of it). Linking needs a session signed in within the last day.
- Tokens are sealed with AES-256-GCM under `PORTAL_CREDENTIALS_SECRETS="2:<key>,1:<key>"`, versioned keys of 32 random bytes in base64 (`openssl rand -base64 32`), apart from `BETTER_AUTH_SECRET`. The app won't start with a `token` portal and no key. Rotating:
  1. add a key with a higher version in front; it seals from then on, the older ones still open
  2. a token sealed under an older version is sealed again under the new one when its user sets it again
  3. take a version off only when nothing needs it: what it sealed, old backups' copies too, is unreadable after
- `oauth` (the portal's consent page) and `connector` (a user's own connector) aren't available: `PORTAL_LINKS` refuses them. A mode the portal's connector doesn't support also stops the app from starting.

#### Fetching with several accounts

Each account is polled on a grid of its own and sees only what the portal shows it. What several accounts see alike is one stored version, so the expensive part is done once:

- a file version (the portal's file, its size and date) is downloaded once, by the first account that sees it open and takes the lease; it is then stored and processed once per content, whoever asked
- a post or course that two accounts see alike is one record; one they see differently is two, each in the views that list it
- the listings are not shared: they cost about ten requests per course per account per pass, so `VIEW_MINUTES` is what to raise on a small portal

| Setting | Default | Meaning |
|---|---|---|
| `VIEW_MINUTES` | 60 | how often each account passes (5 to a day), at an offset its id gives |
| `PUBLISH_DELAY_MINUTES` | 10 | what a pass finds shows this long after its slot (an account's first run's as each pass ends); must be under `VIEW_MINUTES` |
| `HOLD_MINUTES` | 15 | content (bytes, texts, search hits) opens this long after that |
| `CONNECTOR_CONCURRENCY` | 4 | passes one worker runs at once (1 to 64); each asks its portal one thing at a time |
| `CONNECTOR_POLL_TIMEOUT_MINUTES` | 60 | a run longer than this is aborted; also how long a file's fetch lease lasts |

An expired or revoked account isn't polled, and a run the portal refuses the token of marks it revoked until it's linked again.

#### What users can and can't learn of each other

What the hub guarantees:

- a record that isn't yours answers as one that isn't there: the same 404, whether another account sees it or nobody does
- nothing says another user's account already fetched something: ids are random, no hub timestamps are shown, there are no counts or "already synced" states, and an account's items show on its own schedule whether the hub had them or not
- the hold: a file's content opens `HOLD_MINUTES` after the user's own view shows it, the same whether the hub had it or fetched it for this account. Without it, content that opens at once would tell the user that someone else had it (a known side channel of sharing stored data)
- a pass that ends late shows at the next slot, so how long it took tells nothing. An account's first run shows each pass as it ends, which tells its own user only what they know, when they linked it; its content still opens at the hold

What can't be hidden:

- timing under load: when fetching, processing and indexing a file take longer than `HOLD_MINUTES` (a first link of a large course nobody had, an embedding backfill), its texts and search hits come later, which shows it was new to the hub. A longer hold narrows this; none removes it while work is shared
- load on one server: answers are slower while others' runs and searches run, the search index's word statistics are the whole index's, and with a reranker a search made while another is reranked keeps the index's order. These say that others are active, not who or what
- the operator: whoever holds the database and the keys can open every token (the hub has to, to use them), and read everything the hub stores. The portal logs each request as the account that made it, and the hub never asks for anything outside that account's own view

#### Canvas tokens

A token a user pastes has no scopes, so the Canvas client only reads (GET and HEAD), and only from the Canvas the user linked it with, over https. Users link it on the web app's Sources page: their school's Canvas address, a link to where Canvas makes tokens there (`/profile/settings`), and the token.

| | Canvas hosted by Instructure | Self-hosted Canvas |
|---|---|---|
| Users pasting their own tokens | Instructure's API policy says an app used by several users must get their tokens by OAuth, and that asking users to make a token and enter it into a third-party app violates it. The hub refuses a token there (422 `TOKENS_NOT_ALLOWED`): a host under `instructure.com`, or one whose DNS CNAMEs lead there, before the token goes anywhere | governed by the institution's own rules: ask its Canvas admins before opening it |
| OAuth | needs a developer key from the institution; the hub doesn't link by OAuth | the same, if the institution allows it |

- an institution may stop students from making tokens or cap how long one lasts: a student's token can expire, and its account then shows `expired`, or `revoked` once Canvas refuses it, until the user links a new one
- tell the institution what the hub reads and who reads it, whichever Canvas it is

## External connectors

A connector can also run as its own service, in any language, and send data over gRPC (`proto/ingest.proto`). Each one gets a token in `CONNECTOR_TOKENS="portal=token,…"` and sends it as `authorization: Bearer <token>`; the token decides the portal. The hub doesn't schedule these, they sync when they want.

A `FileRecord`'s `updated_at` is the file's date on the portal, its content's: users see it as when the file changed, and a new one makes the hub ask for the content again. Leave it out when the portal has none, never the time of the sync.

Of a portal set to `public` (Public portals, above), the connector sends the site's whole directory as `Course`s (a catalog that changes slowly needs it once a week or so), and asks `Wanted` which of them users want: their ids as `Course` sent them, picked now or within 14 days of their last pick, nothing of who picked them or how many. It sends posts and files of those alone, and of any it syncs anyway by its own settings; a course that drops out of `Wanted` it keeps as it was, removing nothing and keeping its state, so a pick later goes on from there. Of a portal that isn't public, `Wanted` answers none.

A refused call's status says what to do: `INVALID_ARGUMENT` fix the record or skip it, `FAILED_PRECONDITION` send what it refers to first (a course before its posts), `DATA_LOSS` send the content again, `ABORTED` or `UNAVAILABLE` try again later. When the hub refused it, the `grpc-status-details-bin` trailer also has gRPC's standard `google.rpc.Status` with a `google.rpc.ErrorInfo`: `domain` is `unihub` and `reason` a name that never changes, to switch on instead of the message:

- `INVALID_RECORD`: not the shape the proto describes (a Content stream out of order too), or text and json postgres can't keep
- `FILE_COURSE_MISMATCH`: a file names a course, and a post in another one
- `UNKNOWN_REFERENCE`: a course, post or file never sent
- `CONTENT_TOO_LARGE`: content past `STORAGE_MAX_FILE_MB`

Most gRPC libraries decode the trailer themselves: in Go `status.FromError(err)` and `.Details()`, in Java `StatusProto.fromThrowable()`, in Python `rpc_status.from_call()` from `grpcio-status`. In Node, decode it as `google.rpc.Status` with protobufjs and Google's `google/rpc` protos (a copy is in `proto/google/rpc`), as `test/grpc.e2e-spec.ts` does.

The gRPC server starts only when some token is set and listens on `GRPC_URL` without TLS, so keep it on a private network or behind a TLS proxy.

File content, from either kind of connector, is kept once per sha256 under `STORAGE_PATH`. One file may take up to `STORAGE_MAX_FILE_MB` (1024 MiB by default): past that the upload is refused as an invalid record (`INVALID_ARGUMENT` over gRPC) and nothing of it is kept. A file whose declared size is past it is answered `needsContent: false`, so a connector doesn't send it on every sync; one without a size should not resend refused content until `File` answers `changed` for it.

## Deploy

`deploy/compose.yml` runs the hub on one server: caddy (TLS from Let's Encrypt) in front of the app, postgres and redis, and with its `search` profile OpenSearch and the models (Deploying search, below).

```bash
cp deploy/.env.example deploy/.env   # then fill it in
docker compose -f deploy/compose.yml up -d --build
# the first admin, with the build image's tools
docker compose -f deploy/compose.yml run --rm migrate npm run auth:create-admin -- --email you@example.com --password '…'
```

- the `migrate` service applies prisma's and the outbox's migrations before the app starts
- `/api/health` checks the database and redis; compose waits for it
- external connectors reach gRPC through caddy over TLS on the same address (`DOMAIN:443`); the gRPC port isn't published
- logs are capped per container
- behind a proxy that puts the client's address in a header of its own, `CLIENT_IP_HEADERS` names it (comma separated, lower-cased; the first one set wins) for Better Auth's per-address rate limits. By default it reads `X-Forwarded-For` and, finding more than one address there, knows none. Behind Cloudflare, `CLIENT_IP_HEADERS=cf-connecting-ip`: Cloudflare sets it and overwrites what a client sends. Set it only when every request comes through that proxy; otherwise a client sends the header itself and picks the address its limits count under. The hub's own limits go by Express's `req.ip` and `TRUST_PROXY` (1 behind one proxy, which takes the right-most `X-Forwarded-For` entry, the one the proxy added), so they need no header setting
- give the domain an A record only (or turn on IPv6 in docker): docker forwards IPv6 through its proxy, and every IPv6 client would show up with one address
- backups: `deploy/backup.sh <folder>` from cron dumps the database and copies new files; keep the folder, and `deploy/.env`, off the server too. The search index needs none (below)

Restoring, into an empty stack with the same `deploy/.env`:

```bash
docker compose -f deploy/compose.yml up -d postgres
docker compose -f deploy/compose.yml exec -T postgres pg_restore -U unihub -d unihub --no-owner < backups/db-<date>.dump
docker compose -f deploy/compose.yml create app   # makes the blobs volume
rsync -a backups/blobs/ "$(docker volume inspect -f '{{ .Mountpoint }}' unihub_blobs)/blobs/"
chown -R 1000:1000 "$(docker volume inspect -f '{{ .Mountpoint }}' unihub_blobs)"
docker compose -f deploy/compose.yml up -d
```

Updating: back up, `git pull`, then `up -d --build` again. The old app keeps running while `migrate` applies the new schema, so a migration only adds until the code that needed the old shape is gone; going back past a migration means restoring a backup. One that moves data elsewhere keeps the old columns and refuses what the old app would still write to them, as a write conflict, so its connectors try again later, by then on the new app (`20261106120000_catalog_versions`, catalog's records into versions); its reads go on meanwhile.

Published images: after CI passes on main, `.github/workflows/release.yml` pushes two images of that commit, tagged with its full sha, to GitHub's container registry: `ghcr.io/dmitry-maslakov/unihub`, the app, and `ghcr.io/dmitry-maslakov/unihub-migrate`, the `build` stage the `migrate` service runs. A deployment can pull a version instead of building it, and go back to an older one without a rebuild.

### Heavy processors

A processor with `heavy` (Plugins, above) doesn't run in the `plugins` queue, so text extraction never waits for a model: its jobs, the first pass for stored content and the reconcile's alike (both queue through `PluginJobQueue`, which picks the queue by the processor's spec), wait in the `models` queue, same job shape, retries and outage pause as `plugins`'. Nothing reads it in the api, the `worker` or `all`: its jobs wait until a batch run drains them, and a model server can be started for the run and stopped after it.

- `APP_ROLE=models` is that run: the same image and command, with the same settings (`STORAGE_PATH` shared with the worker, `DATABASE_URL`, `REDIS_URL`). It consumes only `models`, one job at a time, and has no scheduler, no outbox relay, no connectors and no HTTP or gRPC server. It exits with code 0, after shutting down as SIGTERM does, once the queue has nothing waiting, active or delayed (a retry's backoff); started with nothing to do, it exits at once. Each job gets its processor's `timeoutMinutes` and is tried again like any other, up to 5 attempts; SIGTERM puts a job being run back to wait, without spending an attempt. What it makes is saved as the worker's processors do; a text it hands to the search index waits in `search-index` for the worker
- `npm run models:pending` (`node dist/main.js models-pending`) asks whether there's work without starting the app: plain BullMQ on `REDIS_URL`, it prints the count of jobs to do (as the run counts them) and exits 0 when there are some, 3 when there are none, and anything else (1) when it can't tell (Redis away included, within a few seconds), so a CronJob starts a model only when there's work. A job already active counts, so the CronJob needs `concurrencyPolicy: Forbid` (or the equivalent in another scheduler), or a second model starts beside a running one
- the queue shows in the metrics as `unihub_queue_jobs{queue="models"}` like the others, read by the worker. A heavy job's outcomes count in `unihub_plugin_jobs_total` as the rest, but only while the run is up, which exits seconds after the last job, so watch heavy dead letters with `unihub_queue_jobs{queue="models",state="failed"}`, which the worker reads. A processor whose model can't be reached throws `ModelUnavailableError`: the queue pauses and the job waits, no attempt spent

### Running the API and the worker apart

By default one process runs it all (`APP_ROLE=all`, which leaves the `models` queue alone), as `deploy/compose.yml` does: an error that crashes background work then takes the API down with it, and parsing or embedding a large file takes the CPU the API answers with. `APP_ROLE` splits them into two processes of the same image and command (`node dist/main.js`), with the same settings otherwise:

- `api`: the HTTP app (REST, sign-in, the OpenAPI docs, MCP) and gRPC ingest. It adds work and runs none of it: an upload writes its outbox messages, "sync now" queues a poll
- `worker`: the queues' workers (`connectors`, `plugins`, `search-index`), the crons (the reconciles, the outbox's cleanup), what runs once at start (the reconciles, the poll connectors' schedules, the push connectors) and the outbox relay, which hands the api's messages to the queues on its next poll, within a second. A standalone Nest app, with no HTTP or gRPC server: `PORT`, `TRUST_PROXY` and `GRPC_URL` are the api's
- `models`: only the batch run that drains the heavy processors' queue and exits (Heavy processors, above)
- both need the same `STORAGE_PATH`, on storage they share: the api keeps the content gRPC connectors upload and serves what's kept (`GET /api/files/{id}/content`), the worker's connectors keep theirs, and its processors read it all
- the worker serves nothing but its metrics (with `METRICS_PORT`: Metrics, below), so there is no `/api/health` to ask: it's alive while its process runs (an error at startup or one nothing catches ends it, for the restart policy to start it again), it logs `worker started` once up, and its workers show in Redis's `CLIENT LIST`, one connection per queue named `bull:` and the queue's name in base64 (BullMQ's `Queue.getWorkers()` reads the same). SIGTERM stops it as it stops the app, so give it the same grace for jobs to finish. A worker service in compose made from `app` keeps its `stop_grace_period` (30 s) but needs `healthcheck: { disable: true }`: the one it would inherit asks `/api/health`, and it would never be healthy
- one worker is expected. Another would be safe for the outbox relay (its claims are leased, under `FOR UPDATE SKIP LOCKED`), the crons and the schedules (what they queue is deduplicated, a schedule is set by its key), but it doubles each queue's concurrency (`search-index` would run two jobs at a time, not one) and runs every push connector again: `RUN_CONNECTORS=false` on all but one
- one api too: the rate limits (Better Auth's, MCP's) are kept in its memory

### Metrics

With `METRICS_PORT` set, each process, the api and the worker alike, serves Prometheus metrics for a scraper at `/metrics` on that port, and on no other: OpenTelemetry's Prometheus exporter on the app's own meter provider, read when a scrape asks, nothing sent anywhere. Unset, nothing is served. It listens on every interface, as the app does, without auth, and the metrics say what the hub runs and how busy it is: keep the port on the private network the scraper is on and never publish it (no `ports:` in compose, nothing in caddy). The app's `PORT` is refused, and a port in use stops the app at start.

- every process: its CPU (`process_cpu_time_total`, `process_cpu_utilization`), memory (`process_memory_usage`, the RSS in bytes, and `v8js_memory_heap_*` by heap space), the event loop's delay since the last scrape (`nodejs_eventloop_delay_p99` and the others, in seconds) and its utilization, and GC (`v8js_gc_duration` by kind)
- the worker, the queues: `unihub_queue_jobs{queue, state}` of `connectors`, `plugins`, `models` and `search-index` (with search on), `waiting`, `active`, `delayed` (a retry's backoff too) and `failed` (given up for good, kept as long as the queue keeps them, 7 or 14 days). `connectors`' `delayed` is mostly each poll schedule's next tick, so it's never 0 and no backlog. `unihub_queue_rate_limited{queue}` is 1 while one waits out an outage (Search index, above, and the database for `plugins` and `models`). Read from Redis by the worker alone, so an api beside it doesn't count them again, within 2 s; `unihub_queue_counts_read` is 0 for a scrape that couldn't read them (Redis away, slow or failing, logged unless it's away), and the counts then hold their last reading
- the worker, connectors and plugins: `unihub_connector_runs_total{portal, outcome}`, polls `succeeded` or `failed` and push runs `ended` or `failed`; `unihub_connector_last_success_timestamp_seconds{portal}`, when a poll last succeeded in this process (none after a restart until one does); `unihub_plugin_jobs_total{plugin, outcome}`, each attempt `completed` or `failed`, and `unihub_plugin_dead_letters_total{plugin}`, the jobs that gave up for good
- the api, search: `unihub_search_duration_seconds{outcome}`, a histogram of searches `ok` or `failed`, and `unihub_search_rerank_fallbacks_total{reason}`, those in the index's order as the reranker was `busy`, `away`, past its time (`timeout`) or `failed` otherwise

Labels come from fixed sets (queues, states, portals, the plugins turned on, outcomes, reasons), never an account, a user, a file or a course. With `APP_ROLE=all` one port serves all of it. NestJS Observe, once linked (AGENTS.md), sends its telemetry from OpenTelemetry's global providers; these metrics stay on the app's own, served only to the scraper, so the two never mix.

### Deploying search

With the search lines of `deploy/.env.example` uncommented in `deploy/.env` (`COMPOSE_PROFILES="search"` among them, and `TEI_TAG` on an arm64 server), `up -d` also starts OpenSearch, two TEI servers of `BAAI/bge-m3` (`embedder` for indexing, `embedder-query` for searches, so a search never waits behind indexing) and the reranker, whose model `reranker-init` puts in place once. Without them, as in CI's smoke run, there's no search. Only the compose network reaches them: OpenSearch runs without users or TLS and holds the text of every file, so never publish its port, nor the models'. These services extend `docker-compose.yml`'s, where the models and their revisions are pinned once, and drop its ports with `!reset`: the server needs the whole checkout and Docker Compose 2.24 or later. The app waits for none of them (Search index, above, says what it does while one is away). The `curl` commands below run in OpenSearch's container, after `docker compose -f deploy/compose.yml exec opensearch`.

- the host needs `vm.max_map_count` of at least 262144: `sudo sysctl -w vm.max_map_count=262144`, and the line `vm.max_map_count=262144` in `/etc/sysctl.d/99-opensearch.conf` to keep it after a reboot
- memory, by the limits: OpenSearch 4 GB (`OPENSEARCH_MEMORY`), each TEI server 3 GB, so 13 GB for search alone and a server of 16 GB. OpenSearch's heap is 2 GB (`OPENSEARCH_HEAP`), locked in memory so it's never swapped out, and at most half its memory, as Lucene's files and the vectors' graphs take the rest: a larger heap needs a larger `OPENSEARCH_MEMORY` with it. Once the index is filled, `curl -s 'localhost:9200/_nodes/stats/jvm?filter_path=**.heap_used_percent'` shows how much of the heap it takes. The TEI servers take whatever cores are free; `TEI_CPUS` caps each, no more than the server has (docker refuses that)
- disk: the models take 2.9 GB of the `models` volume, downloaded on the first start (bge-m3 2.3 GB, the reranker 0.6 GB). That first `up` waits for `embedder` to download its model before it starts `embedder-query`, which reads the same files: a TEI that finds another downloading them gives up on them and starts on another backend from another copy, its vectors a little off. The index takes about four times the texts, and 4 KB a chunk for its vector: under a GB for 50,000 chunks
- backfill: once search is on, and after each new generation or model (Search index, above), the reconcile queues every text of the processors that are on, embedded one at a time, 8 chunks at a time. That's about 2.6 chunks a second on 6 arm cores, some 4 hours for 40,000 chunks (about 20,000 pages), and 1.1 a second on 4 amd64 cores (Zen 2), some 10 hours. Searches work meanwhile, by meaning too, but find only what's in so far; it's done once the hourly reconcile no longer logs `queued … search index jobs`. The records, a job each, came without a new generation: the first reconcile on an index of texts alone queues every post, file with content and tree, and the texts stay as they are. A record written the first time waits for no refresh: a file's name or a tree, not embedded, takes a database read and a few milliseconds of OpenSearch, so 10,000 of them go in within minutes. A post's strings are read in a worker thread of their own, about 0.1 s each on arm, and the post is embedded on its own, its 1 or 2 chunks a call (a module's titles or an announcement are short, a page longer), so at the rates above, which are 8 chunks a call, 5,000 posts of some 7,500 chunks take at least 50 minutes on 6 arm cores and 2 hours on 4 amd64 ones. After that, a post edited past its text (a link, a date) has only its fingerprint written, and one whose text changed is embedded again, alone. A new generation or model fills them again with the texts
- the reranker, which a search waits on: on amd64 (Zen 2), with the embedders idle, a snippet takes it about 200 ms at 4 cores and 140 ms at 8, 8 snippets at a time, so the 20 it takes by default come to 3 to 4 s, near the 5 s after which a search keeps the index's order. During the backfill it shares the server's cores with `embedder`, which takes them all unless `TEI_CPUS` caps it, and goes past 5 s more often. One user at the search limit (20 a minute) keeps it busy the whole minute, the others' searches then in the index's order. `RERANK_CANDIDATES=10`, as many files as a search answers by default, takes about 1.4 s at 8 cores, but reorders only the 10 the index puts first. On 6 arm cores the 20 take about 1.3 s
- a disk past OpenSearch's flood stage (95% used) makes the index read-only: searches go on, indexing waits (logged, as an error every 10 minutes), and past 90% (the high watermark) no index is made either. Free space (`docker image prune`, old generations below) until the disk is under 90%, not just under 95%: OpenSearch then lifts the block itself within half a minute, and the queue goes on. `curl -s 'localhost:9200/_cat/allocation?v'` shows the disk as it sees it
- old generations: a new generation or model is a new index, filled next to the old one, which stays until it's deleted by hand once the new one is done. `curl -s 'localhost:9200/_cat/indices/unihub-*?v'` lists them, `curl -s -X DELETE localhost:9200/unihub-texts-g1-bm25` deletes one
- no backup: the index is made of postgres alone, so `backup.sh` leaves out the `osdata` and `models` volumes. Restored onto a new server, or with `osdata` lost, the models are downloaded again and the reconcile fills the index again, as in the backfill above
- a snippet is plain text with whatever HTML its file had (REST API, Search): a web page shows it as text (`textContent`), never as HTML, or a file's markup runs in the page
